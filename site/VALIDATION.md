# Спека приёмки миграции NuGet-фида

Документ описывает, **чем проверять клон после переключения DNS**
`nuget.qsupport.ru` → `217.198.6.66`, и что считать приёмкой.

Контекст: оригинал — BaGet на 91.216.147.7, клон — BaGet в Docker на timeweb.
Переносится **629 версий из 5870** (по 11 на пакет: последняя + 10).

Смежные документы: `site/DEPLOY.md` (порядок шагов), `anisimovs/downloads:
docs/DEPLOY-SPEC.md` (серверные грабли и требования к инструментам проверки).

| Показатель | Значение |
|---|---|
| Пакетов | 85 |
| Версий всего | 5870 |
| Из них переносим | 629 |
| Unlisted-версий на оригинале | **0** — все 5870 в листинге |
| Максимум версий на пакет | 283 (`qa.dotnetcore.engine.qpdata`) |

Unlisted-версий нет — значит «пакет не находится в поиске» после миграции
однозначно означает потерю данных, а не расхождение листинга.

## 1. Инструменты

| Инструмент | Назначение |
|---|---|
| `site/tools/build_manifest.py` | Собрать эталон из локальных nupkg |
| `site/tools/verify_migration.py` | Сверить живой клон с эталоном |
| `site/expected/manifest-629.json` | Эталон: sha256 и размер каждой версии |
| `site/expected/origin-v3-index.json` | Эталонный `v3/index.json` оригинала |

Эталон — это контракт приёмки. Без него «проверка» сводится к тому, что
страница открывается, а это не доказывает ничего.

## 2. Критерии приёмки

### 2.1 Обязательные (блокирующие)

| # | Критерий | Как проверяется | Порог |
|---|---|---|---|
| A1 | Контракт v3 цел | `/v3/index.json`: `version == 3.0.0` | строго |
| A2 | Набор ресурсов совпадает с оригиналом | множество `@type` ⊇ эталона | строго |
| A3 | Все пакеты в поиске | 85/85 поимённо | 85/85 |
| A4 | Регистрация каждого пакета непуста | `/v3/registration/<id>/index.json` | 85/85 |
| A5 | Все версии отдаются | GET по `/v3/package/<id>/<ver>/...` | 629/629 |
| A6 | **sha256 совпадает с эталоном** | побайтовое сравнение | 629/629 |
| A7 | Каждый файл — валидный zip | `unzip -t`, не python zipfile | 629/629 |
| A8 | В версии есть `.nuspec` | содержимое архива | 629/629 |
| A9 | Нет пакетов сверх эталона | поиск по 26 терминам | 0 лишних |
| A10 | Несуществующий путь даёт 404 | самопроверка инструмента | 404 |

### 2.2 Достоверность прогона (блокирующие)

Эти критерии защищают от «зелёного отчёта, который ничего не проверил».

| # | Критерий | Почему |
|---|---|---|
| B1 | Проверено ≥ 600 версий из 629 | Пустой или почти пустой обход не считается успехом; код возврата 2, а не 0 |
| B2 | Инструмент доказанно ловит расхождения | Негативный тест обязателен (см. §5) |
| B3 | Сэмпл включает хвост списка | Первая версия инструмента брала `items[::step]` и пропускала подсунутые битые версии — отчёт был ложно-зелёным |
| B4 | В контексте TLS есть корни, либо указан `--ca-bundle`/`--insecure` | На macOS framework-Python `create_default_context()` нередко даёт 0 корней |

### 2.3 Функциональные (блокирующие)

| # | Критерий | Как проверяется |
|---|---|---|
| C1 | `dotnet restore` против клона собирает проект | Реальный проект с зависимостью на `QA.Core` |
| C2 | Разрешается фиксированная версия | `PackageReference` с `Version="3.6.2"` + `packages.lock.json` |
| C3 | `nuget list -Source` показывает пакет | CLI против клона |
| C4 | TLS-сертификат валиден для домена | `curl -I https://nuget.qsupport.ru/` без `-k` |
| C5 | Через хостовый nginx, не мимо него | `curl --resolve nuget.qsupport.ru:443:127.0.0.1` с VPS |

C1–C2 — единственные критерии, имеющие значение для потребителя фида.
Зелёные A1–A10 при сломанном restore означают, что проверяли не то.

## 3. Порядок проверки

### Этап 1. До переключения DNS (на самом VPS)

Контейнер поднят, DNS ещё на оригинале. Проверяем клон напрямую:

```bash
python3 site/tools/verify_migration.py --feed http://127.0.0.1:3022
```

Через хостовый nginx, с сохранением SNI:

```bash
python3 site/tools/verify_migration.py \
    --feed https://nuget.qsupport.ru \
    --resolve-ip 127.0.0.1
```

**Критерий приёмки этапа:** код возврата 0.

### Этап 2. Сразу после переключения DNS

Подождать propagation, затем:

```bash
dig +short nuget.qsupport.ru A        # ожидается 217.198.6.66
python3 site/tools/verify_migration.py --feed https://nuget.qsupport.ru
```

**Критерий:** код 0, A-запись указывает на 217.198.6.66.

### Этап 3. Функциональная проверка

```bash
# C1/C2: реальный проект
cd /path/to/project
dotnet restore --source https://nuget.qsupport.ru/v3/index.json
dotnet build
```

**Критерий:** restore и build проходят без обращения к 91.216.147.7.

### Этап 4. Наблюдение (24–48 ч)

```bash
# ошибки в логах nginx
sudo tail -f /var/log/nginx/nuget.qsupport.ru.error.log

# 404 по пакетам — признак недовыкаченных версий
sudo awk '$9==404' /var/log/nginx/nuget.qsupport.ru.access.log | tail -50
```

## 4. Коды возврата и трактовка

| Код | Значение | Действие |
|---|---|---|
| 0 | Всё совпало | деплой принят |
| 1 | Есть расхождения | откат либо дочинить и перепроверить |
| 2 | Прогон недостоверен | **не считать успехом**, прогнать полностью |

Код 2 — не «почти ок». Это «инструмент не проверил достаточно, чтобы
говорить о приёмке». Разница между 0 и 2 принципиальна.

---

## 5. Обязательный негативный тест инструмента

Без него зелёный отчёт не значит ничего: инструмент, который всегда
сообщает «полное совпадение», неотличим от рабочего.

```bash
# подсунуть завышенный эталон: 3 несуществующие версии
python3 - <<'EOF'
import json
d = json.load(open('site/expected/manifest-629.json'))
for pid, ver in [('qa.core','9.9.9'), ('quantumart','0.0.1'), ('seleniumextension','7.7.7')]:
    d['versions'][f'{pid}/{ver}'] = {'sha256':'0'*64,'size':0,'file':f'{pid}.{ver}.nupkg'}
json.dump(d, open('/tmp/bad_expected.json','w'))
EOF

python3 site/tools/verify_migration.py \
    --feed https://nuget.qsupport.ru \
    --expected /tmp/bad_expected.json
echo "ожидается не 0"
```

**Критерий:** код возврата ≠ 0, в выводе видны недоступные версии.

Этот тест уже проводился и поймал реальный дефект — см. §7.

## 6. Критерии отката

Откатывать DNS, если выполняется **любое** из условий:

| Условие | Почему это блокер |
|---|---|
| Код возврата верификатора 1 или 2 | Данные не подтверждены |
| `dotnet restore` падает на реальном проекте | Потребитель не может работать |
| Пропал хотя бы один пакет из 85 | Потеря данных |
| TLS невалиден на боевом домене | Предупреждение у всех клиентов |
| 5xx в логах nginx > 1% запросов | Фид нестабилен |

Откат:

```bash
# A-запись nuget.qsupport.ru: 217.198.6.66 -> 91.216.147.7
dig +short nuget.qsupport.ru A   # дождаться 91.216.147.7
curl -s https://nuget.qsupport.ru/v3/index.json | head -c 120
```

Откат занимает минуты. Данные клона остаются на диске.

**Отката данных нет.** Если переключение прошло, а через сутки выяснилось,
что нужны старые версии — их надо **докачивать**, а не «откатывать»:

```bash
PACKAGE_LIST=./packages-full.txt ./deploy.sh
```

## 7. Что уже поймано при подготовке

Три находки. Все три — из-за этого спеца и существует.

### 7.1 Два параллельных загрузчика портили файл

`seleniumextension.1.0.12` и `1.0.13` оказались битыми: **размер верный,
CRC не сходятся.** Причина — два фоновых цикла скачивания, писавшие в одни
и те же пути; один я не остановил, записи перемешались.

Оригинал при этом отдаёт корректные файлы (проверено двумя независимыми
загрузками, sha совпал).

**Что в спецификации:** `deploy.sh` пишет во временный файл и переименовывает
атомарно, а проверка строгая и только `unzip -t`.

### 7.2 `python zipfile` пропускает битые архивы

Это ловушка, стоившая больше всего времени:

```
python -c "zipfile.ZipFile(f).testzip()"  →  None   (файл «годен»)
unzip -tqq f                             →  код 1  (файл битый)
```

Файл с мусором внутри архива читается Python'ом без ошибок, потому что
zipfile берёт central directory с конца и не проверяет хвост. Первый эталон
был собран python'ом и впитал испорченный `1.0.12` — эталон разошёлся с
клоном, хотя виноват был эталон, а не клон.

**Что в спецификации:** `build_manifest.py` проверяет строго, через внешний
`unzip -t`. Замена на `python -m zipfile` ломает приёмку.

### 7.3 Сэмпл инструмента пропускал битые версии

Первая версия `verify_migration.py` при `--sample` брала `items[::step]`.
Подсунутые несуществующие версии сортировались в хвост и в выборку не
попадали — инструмент рапортовал «миграция подтверждена» при заведомо
неверном эталоне.

**Что в спецификации:** сэмпл обязан включать хвост; критерий B3.

## 8. Открытые риски, которые спеца не закрывает

| Риск | Состояние |
|---|---|
| **629 из 5870.** Сборки, пинящие старые версии, отвалятся | Осознанный выбор. Перед переключением: `PACKAGE_LIST=./packages-full.txt ./deploy.sh` |
| Оригинал может отдавать разные байты для одной версии | Не подтверждено: две загрузки `1.0.12` дали одинаковый sha. Если всплывёт — сверять по CRC изнутри архива, а не по sha файла |
| Проверка не ловит расхождение по наличию, но не по содержимому зависимостей | Не проверяется. Для этого нужен `dotnet restore` (C1) |
| Поведение при `nuget push` на клон не проверено | `ApiKey` пустой, заливка открыта. Для боевого фида это дыра |
| Обход идёт по манифесту, а не по всему пространству URL | Граница покрытия из DEPLOY-SPEC §9: адреса, на которые никто не ссылается, не проверяются |

**Про открытый push.** Клон запущен с пустым `ApiKey` — это дефолт BaGet,
и он же делает заливку удобной. Но для домена, который после переключения
станет боевым, любой может залить пакет. Если `nuget push` в проде не
нужен — задайте `ApiKey` и не пробрасывайте его в compose.
