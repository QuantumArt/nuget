# Спека приёмки миграции NuGet-фида

Документ описывает, **чем проверять клон после переключения DNS**
`nuget.qsupport.ru` → `217.198.6.66`, и что считать приёмкой.

Контекст: оригинал — BaGet на 91.216.147.7, клон — BaGet в Docker на timeweb.
Переносится **629 версий из 5870** (по 11 на пакет: последняя + 10).

Смежные документы: `site/DEPLOY.md` (порядок шагов), `anisimovs/downloads:
docs/DEPLOY-SPEC.md` (серверные грабли и требования к инструментам проверки).

| Инструмент | Назначение |
|---|---|

| `site/tools/verify_migration.py` | Сверить живой клон с эталоном |

## 2. Критерии приёмки

### 2.1 Обязательные (блокирующие)

| # | Критерий | Как проверяется | Порог |
|---|---|---|---|
| A1 | Контракт v3 цел | `/v3/index.json`: `version == 3.0.0` | строго |
| A2 | Набор ресурсов совпадает с оригиналом | множество `@type` ⊇ эталона | строго |
| A3 | Все пакеты в поиске | 85/85 поимённо | 85/85 |
| A4 | Регистрация каждого пакета непуста | `/v3/registration/<id>/index.json` | 85/85 |
| A5 | Все версии отдаются | GET по `/v3/package/<id>/<ver>/...` | 629/629 |
| A6 | **sha256 совпадает с эталоном** | побайтовое сравнение | 629/629 |
| A7 | Каждый файл — валидный zip | `unzip -t`, не python zipfile | 629/629 |
| A8 | В версии есть `.nuspec` | содержимое архива | 629/629 |
| A9 | Нет пакетов сверх эталона | поиск по 26 терминам | 0 лишних |
| A10 | Несуществующий путь даёт 404 | самопроверка инструмента | 404 |

### 2.2 Достоверность прогона (блокирующие)

Эти критерии защищают от «зелёного отчёта, который ничего не проверил».

| # | Критерий | Почему |
|---|---|---|
| B1 | Проверено ≥ 600 версий из 629 | Пустой или почти пустой обход не считается успехом; код возврата 2, а не 0 |
| B2 | Инструмент доказанно ловит расхождения | Негативный тест обязателен (см. §5) |
| B3 | Сэмпл включает хвост списка | Первая версия инструмента брала `items[::step]` и пропускала подсунутые битые версии — отчёт был ложно-зелёным |
| B4 | В контексте TLS есть корни, либо указан `--ca-bundle`/`--insecure` | На macOS framework-Python `create_default_context()` нередко даёт 0 корней |

### 2.3 Функциональные (блокирующие)

| # | Критерий | Как проверяется |
|---|---|---|
| C1 | `dotnet restore` против клона собирает проект | Реальный проект с зависимостью на `QA.Core` |
| C2 | Разрешается фиксированная версия | `PackageReference` с `Version="3.6.2"` + `packages.lock.json` |
| C3 | `nuget list -Source` показывает пакет | CLI против клона |
| C4 | TLS-сертификат валиден для домена | `curl -I https://nuget.qsupport.ru/` без `-k` |
| C5 | Через хостовый nginx, не мимо него | `curl --resolve nuget.qsupport.ru:443:127.0.0.1` с VPS |

C1–C2 — единственные критерии, имеющие значение для потребителя фида.
Зелёные A1–A10 при сломанном restore означают, что проверяли не то.

## 3. Порядок проверки

### Этап 1. До переключения DNS (на самом VPS)

Контейнер поднят, DNS ещё на оригинале. Проверяем клон напрямую:

```bash
python3 site/tools/verify_migration.py --feed http://127.0.0.1:3022
```

Через хостовый nginx, с сохранением SNI:

```bash
python3 site/tools/verify_migration.py \
    --feed https://nuget.qsupport.ru \
    --resolve-ip 127.0.0.1
```

**Критерий приёмки этапа:** код возврата 0.

### Этап 2. Сразу после переключения DNS

Подождать propagation, затем:

```bash
dig +short nuget.qsupport.ru A        # ожидается 217.198.6.66
python3 site/tools/verify_migration.py --feed https://nuget.qsupport.ru
```

**Критерий:** код 0, A-запись указывает на 217.198.6.66.

### Этап 3. Функциональная проверка

```bash
# C1/C2: реальный проект
cd /path/to/project
dotnet restore --source https://nuget.qsupport.ru/v3/index.json
dotnet build
```

**Критерий:** restore и build проходят без обращения к 91.216.147.7.

### Этап 4. Наблюдение (24–48 ч)

```bash
# ошибки в логах nginx
sudo tail -f /var/log/nginx/nuget.qsupport.ru.error.log

# 404 по пакетам — признак недовыкаченных версий
sudo awk '$9==404' /var/log/nginx/nuget.qsupport.ru.access.log | tail -50
```

## 4. Коды возврата и трактовка

| Код | Значение | Действие |
|---|---|---|
| 0 | Всё совпало | деплой принят |
| 1 | Есть расхождения | откат либо дочинить и перепроверить |
| 2 | Прогон недостоверен | **не считать успехом**, прогнать полностью |

Код 2 — не «почти ок». Это «инструмент не проверил достаточно, чтобы
говорить о приёмке». Разница между 0 и 2 принципиальна.

## 5. Обязательный негативный тест инструмента

Без него зелёный отчёт не значит ничего: инструмент, который всегда
сообщает «полное совпадение», неотличим от рабочего.

```bash
# подсунуть завышенный эталон: 3 несуществующие версии
python3 - <<'EOF'
import json
d = json.load(open('site/expected/manifest-629.json'))
for pid, ver in [('qa.core','9.9.9'), ('quantumart','0.0.1'), ('seleniumextension','7.7.7')]:
    d['versions'][f'{pid}/{ver}'] = {'sha256':'0'*64,'size':0,'file':f'{pid}.{ver}.nupkg'}
json.dump(d, open('/tmp/bad_expected.json','w'))
EOF

python3 site/tools/verify_migration.py \
    --feed https://nuget.qsupport.ru \
    --expected /tmp/bad_expected.json
echo "ожидается не 0"
```

**Критерий:** код возврата ≠ 0, в выводе видны недоступные версии.

Этот тест уже проводился и поймал реальный дефект — см. §7.

## 6. Критерии отката

Откатывать DNS, если выполняется **любое** из условий:

| Условие | Почему это блокер |
|---|---|
| Код возврата верификатора 1 или 2 | Данные не подтверждены |
| `dotnet restore` падает на реальном проекте | Потребитель не может работать |
| Пропал хотя бы один пакет из 85 | Потеря данных |
| TLS невалиден на боевом домене | Предупреждение у всех клиентов |
| 5xx в логах nginx > 1% запросов | Фид нестабилен |

Откат:

```bash
# A-запись nuget.qsupport.ru: 217.198.6.66 -> 91.216.147.7
dig +short nuget.qsupport.ru A   # дождаться 91.216.147.7
curl -s https://nuget.qsupport.ru/v3/index.json | head -c 120
```

Откат занимает минуты. Данные клона остаются на диске.

**Отката данных нет.** Если переключение прошло, а через сутки выяснилось,
что нужны старые версии — их надо **докачивать**, а не «откатывать»:

```bash
PACKAGE_LIST=./packages-full.txt ./deploy.sh
```

## 7. Журнал граблей

Все находки этого деплоя. Сгруппированы по механизму, а не по хронологии:
повторяющийся механизм — признак системной ошибки, а не невезения. Часть
помечена **[м]** — механизм общий для любого Docker-проекта, а не специфичен
для NuGet; такие вынесены также в `anisimovs/downloads:docs/DEPLOY-SPEC.md` §10.

Каждая запись: что произошло → почему → что теперь в коде.

### 7.1 Конфигурация BaGet

**Ключ `Storage:Path`, а не `FileStorage:Path`.** Официальный Docker-гайд
BaGet предлагает `FileStorage__Path`. В этой версии движка переменная молча
игнорируется, пакеты пишутся в `/app/packages` — слой контейнера. Фид при этом
**работает**, ошибки не видно, и всё теряется при первом `docker rm`.
→ В compose задано `Storage:Path`.

**SQLite-база тоже должна быть в томе.** По умолчанию `Data Source=baget.db`
рядом с бинарём — опять в слое. Индекс и метаданные не переживают пересоздание
контейнера. → `Database:ConnectionString` с явным `/var/baget/`.

**BaGet дописывает `packages` к `Storage:Path`.** Фактический путь —
`baget-data/packages/packages/<id>/<version>/`. Не ищите по `packages/<id>`.

**Healthcheck на `wget` всегда падал.** В образе BaGet (`dotnet aspnet`,
Debian-база) `wget` **отсутствует**, есть только `/usr/bin/curl`. Контейнер
помечался `unhealthy` при полностью рабочем фиде. Настоящая причина —
healthcheck скопирован из compose `downloads`, где образ `nginx:alpine` и
`wget` есть. → Проверка переведена на `curl`, подтверждено на живом
контейнере.

**Образ amd64.** На arm64-хосте Docker печатает предупреждение о несовпадении
платформы. На сервере x86 неактуально, на Mac — учитывать время запуска.

### 7.2 Docker Compose **[м]**

**Коллизия имён проектов — самая опасная находка деплоя.** Compose берёт имя
проекта из **basename каталога** с compose-файлом. Здесь каталог `site/`, и у
проекта `downloads` каталог **тоже** `site/` — оба проекта назывались `site`.
Отсюда `WARN Found orphan containers (downloads-web) for this project`.

Надпись безобидна. Опасна кнопка рядом с ней:

```bash
cd ~/nuget/site && docker compose down --remove-orphans
# → снёс бы и nuget-baget, и downloads-web, то есть уронил бы боевой
#   downloads.quantumart.ru
```

Проверено на контейнере-подставке с меткой `project=site`: до фикса
`down --remove-orphans` удалял оба контейнера, после — только свой.
→ В compose прописано `name: nuget` явно. **У `downloads` риск зеркальный** —
ему нужен `name: downloads`.

**`xargs -I{}` не масштабируется.** На 629 аргументах: `xargs: command line
cannot be assembled, too long`. → Скрипт написан на цикле.

### 7.3 Целостность файлов

**Два параллельных загрузчика портили пакет.** `seleniumextension.1.0.12` и
`1.0.13` оказались битыми: **размер верный, CRC не сходятся**. Два фоновых
цикла скачивания писали в одни и те же пути, один я не остановил, записи
перемешались. Оригинал отдаёт их корректно — проверено двумя независимыми
загрузками, sha совпал. → `deploy.sh` пишет во временный файл и переименовывает
атомарно.

**`python zipfile` пропускает битые архивы.** Ловушка, стоившая больше всего
времени:

```
python -c "zipfile.ZipFile(f).testzip()"  →  None    (файл «годен»)
unzip -tqq f                             →  код 1   (файл битый)
```

Файл с мусором внутри архива читается Python'ом без ошибок: zipfile берёт
central directory с конца и не проверяет хвост. Первый эталон был собран
python'ом, впитал испорченный `1.0.12` и **обвинил клон**, который был прав.
→ `build_manifest.py` проверяет строго, только внешним `unzip -t`. Замена на
`python -m zipfile` ломает приёмку.

### 7.4 Инструмент проверки

**Валидатор с выдуманными версиями протокола.** Первая версия требовала
`SearchQueryService/3.5.0` и `RegistrationsBaseUrl/3.0.6`. BaGet публикует
`3.0.0-rc` и `3.0.0-beta` — а набор ресурсов клона оказался **идентичен**
оригиналу, и инструмент рапортовал три расхождения. → Проверяются семейства
ресурсов (версия отбрасывается) плюс полное совпадение с эталонным
`v3/index.json` оригинала.

**`take=1` в поиске даёт ложный провал.** На `q=quantumart` первым
возвращается `NLog.QuantumArt.PrtgMonitoring`, а не `Quantumart`. → `take=100`
с проверкой вхождения.

**Пустой `q=` отдаёт 0 результатов** при полном фиде. Это поведение BaGet,
и в интерфейсе читается как «фид пуст». → Проверять поимённо.

**Сэмпл пропускал битые версии.** `items[::step]` не брал хвост списка;
подсунутые несуществующие версии туда сортировались и в выборку не попадали.
Инструмент рапортовал «миграция подтверждена» при заведомо неверном эталоне.
→ Сэмпл обязан включать хвост; критерий B3.

**`bash -n` не ловит рантайм-баги** — см. 7.5. → Скрипт прогоняется целиком на
манифесте из двух пакетов перед применением к боевому фиду.

### 7.5 Ошибки в собственном коде, пойманные боевым запуском

**`set -u` убил деплой на шаге 3.** Баннер шага ссылался на `SOURCE_FEED` —
переменную, заменённую на `ORIGIN_HOST/ORIGIN_IP` при переходе на
`curl --resolve`, но забытую в строке `echo`. `bash -n` это пропускает: синтаксис
валиден, падает в рантайме. → Строка исправлена.

**Парсер id/версии ломался на id с цифрами.**

```
qp8.infrastucture.1.0.0.nupkg  ->  id='qp'  ver='8.infrastucture.1.0.0'
```

Идентификаторы NuGet содержат цифры (`qp8.*`, `qp8backendapi.*`), а разбор
«первый сегмент, начинающийся с цифры» на этом ломается. На заливку не
влияло, но оптимизация молча не работала. → Шаг заливки берёт id и версию из
URL **манифеста**, где они уже разделены, а не из имени файла.

**Smoke-тест с захардкоженным пакетом.** Проверял фиксированный `qa.core 3.6.2`
— на урезанном манифесте его нет, тест падал на 404 при успешном деплое. →
Пакет берётся первым из манифеста.

### 7.6 Git **[м]**

**Вложенные кавычки в credential helper ломают авторизацию.**
`git -c credential.helper='!f() { ... password="$GH_TOKEN"; }; f'` вернул 403,
хотя API подтверждал `push: True`. → Изолирующий тест: `git fetch` с токеном
в URL. Если он проходит, а обычный — нет, дело в helper'ах, не в токене.

**Пуш с токеном в URL сохраняет токен в `.git/config`** — и в секции
`branch.<name>.remote`, и в выводе команды. → После пуша: `git remote set-url`
на чистый URL и `git config branch.main.remote origin`. Проверять грепом по
`.git/config` и по истории.

**Публичный репозиторий снимает проблему первого клона.** Для
`QuantumArt/nuget` `git clone` работает анонимно, `.credentials.env` для клона
не нужен — он нужен только для `git pull` внутри `deploy.sh`, и то из-за
глобального store на VPS. → `deploy.sh` тянет анонимно при отсутствии
`GH_TOKEN`, а не вручает git пустой пароль.

### 7.7 Окружение **[м]**

**Устаревший bind-mount после пересоздания каталога (macOS/Docker Desktop).**
Каталог тома удалили и создали заново, а контейнер видел старую копию (метка
времени на 4 часа давнее) и не мог открыть файл даже под root:
`SQLite Error 14: unable to open database file` и 500 на всех пакетах. При этом
`/v3/index.json` отдаёт 200, а контейнер помечен `healthy` — то есть ни
healthcheck, ни smoke-тест главной страницы это **не замечают**.
→ Том пересоздан с нуля, данные залиты заново, проверка сошлась 629/629.
Полезно знать: **проверять надо скачиванием пакета, а не кодом `/`** — на
macOS это единственный способ поймать такой сбой.

## 8. Открытые риски, которые спеца не закрывает

| Риск | Состояние |
|---|---|
| **629 из 5870.** Сборки, пинящие старые версии, отвалятся | Осознанный выбор. Перед переключением: `PACKAGE_LIST=./packages-full.txt ./deploy.sh` |
| Оригинал может отдавать разные байты для одной версии | Не подтверждено: две загрузки `1.0.12` дали одинаковый sha. Если всплывёт — сверять по CRC изнутри архива, а не по sha файла |
| Проверка не ловит расхождение по наличию, но не по содержимому зависимостей | Не проверяется. Для этого нужен `dotnet restore` (C1) |
| Поведение при `nuget push` на клон не проверено | `ApiKey` пустой, заливка открыта. Для боевого фида это дыра |
| Обход идёт по манифесту, а не по всему пространству URL | Граница покрытия из DEPLOY-SPEC §9: адреса, на которые никто не ссылается, не проверяются |

**Про открытый push.** Клон запущен с пустым `ApiKey` — это дефолт BaGet,
и он же делает заливку удобной. Но для домена, который после переключения
станет боевым, любой может залить пакет. Если `nuget push` в проде не
нужен — задайте `ApiKey` и не пробрасывайте его в compose.
