# DEPLOY — клон NuGet-фида на VPS timeweb

Домен: **`nuget.qsupport.ru` — боевой.** Переключение DNS переводит реальные
сборки QuantumArt с оригинала (91.216.147.7) на клон (217.198.6.66).
Выполняет Slava, скрипты и конфиги подготовлены заранее.

Общая механика деплоя и все серверные грабли описаны в
`anisimovs/downloads:docs/DEPLOY-SPEC.md` — здесь только специфика этого
проекта. **Прочитай DEPLOY-SPEC §3 про авторизацию git: без неё `git pull`
на этом VPS даёт 403.**

## Ключ публикации (`ApiKey`)

По умолчанию BaGet запускается с пустым `ApiKey` — **пуш открыт для всех**.
На боевом домене это значит, что любой может залить пакет в ваш фид.

Ключ задаётся через `.env` рядом с `docker-compose.production.yml`:

```bash
cd ~/nuget/site
echo "BAGET_APIKEY=$(openssl rand -hex 24)" > .env
chmod 600 .env
docker compose -f docker-compose.production.yml up -d
```

`.env` в `.gitignore`, в репозиторий не попадает. Генерируйте **новый на
каждом сервере**, не переносите ключ из одного окружения в другое.

**Ключ влияет только на публикацию.** Чтение — `restore`, поиск, скачивание —
остаётся открытым, поэтому клиенты ничего не заметят. Проверено на живом
контейнере:

| Запрос | Без ключа | С неверным | С верным |
|---|---|---|---|
| `PUT /api/v2/package` | 401 | 401 | **201** |
| `GET /v3/index.json` | 200 | — | 200 |
| `GET` скачивание пакета | 200 | — | 200 |

`deploy.sh` и `bootstrap.sh` читают ключ из того же `.env` и подставляют его
в заголовок `X-NuGet-ApiKey`, поэтому после включения ключа они продолжат
работать. Проверено: `bootstrap.sh` с ключом — 629/629, приёмка код 0.

**Отключить обратно:** удалить `.env` и пересоздать контейнер — пуш снова
станет открытым.

## Восстановление с нуля (без оригинала)

Пакеты лежат в репозитории, в каталоге `packages/` — 629 файлов `.nupkg`
(165 МБ). Оригинал на `91.216.147.7` для восстановления **не нужен**.

```bash
git clone https://github.com/QuantumArt/nuget.git ~/nuget
cd ~/nuget/site
./bootstrap.sh
```

`bootstrap.sh` проверяет каждый файл по эталону `expected/manifest-629.json`
**до** запуска контейнера, поднимает BaGet, заливает пакеты и прогоняет
приёмку. Если хоть один файл не сошёлся по sha256 — фид не поднимается
вовсе, чтобы сломанные данные не оказались в проде.

Когда пользоваться: оригинал выключен, VPS переустановлен, разворачиваете
фид на новой машине.

Отличие от `deploy.sh`: тот качает с боевого фида (адрес закреплён на
`91.216.147.7` через `curl --resolve`), этот берёт локальные файлы и сети
не требует.

> Проверено на пустом томе: 629/629 залито, приёмка код 0.

## Риск, о котором нужно знать до переключения

**В клоне 629 версий вместо 5870. Старые версии после переключения перестанут
резолвиться, и `dotnet restore` с зафиксированной старой версией упадёт.**

Это прямое следствие решения взять только 11 версий на пакет. Если сборки
QuantumArt где-то пинят `QA.Core 3.4.0` или подобное, они отвалятся.

Что с этим можно сделать — решай до шага 4:

**Вариант А. Перекачать всю историю (рекомендую для боевого переключения).**
Манифест уже подготовлен, 5870 URL:

```bash
cd ~/nuget/site
PACKAGE_LIST=./packages-full.txt ./deploy.sh
```

Это ~200 МБ и около 15–20 минут. Ровно этот путь и есть то, что делает
переключение безопасным.

**Вариант Б. Оставить как есть** и принять, что сборки на старых версиях
упадут; чинить адресно, по мере поступления заявок.

Отката «частично» нет: после переключения домена фид один.

**Чего зеркалирование НЕ чинит.** У BaGet есть встроенный `Mirror`, и он тут не
помогает: сертификат оригинала покрывает ровно один SAN — `nuget.qsupport.ru`.
Алиаса с валидным сертификатом, указывающего на 91.216.147.7, не существует
(`cluster.quantumart.ru` отдаёт сертификат `smart-widget.qsupport.ru` и NuGet
API не отдаёт). Если клон начнёт зеркалить по имени — он зазеркалит сам себя.

## Шаг 0. Проверить порт и DNS

```bash
docker ps --format '{{.Names}}\t{{.Ports}}'
ss -ltnp | grep 3022
dig +short nuget.qsupport.ru A
```

Занятые порты на момент настройки: 3001, 3010, 3020, 3021, 5000, 7700, 8090,
9117. **3022 должен быть свободен.** Если занят — правь
`docker-compose.production.yml` и `nginx/nuget.qsupport.ru` синхронно,
номер порта в обоих должен совпадать.

## Шаг 1. Сертификат — ДО переключения DNS

Общий SAN-сертификат VPS (`ts.sqlhub.pro`) покрывает только `*.sqlhub.pro`,
для этого домена не подходит. Нужен отдельный:

```bash
sudo certbot certonly --dns-cloudflare \
  --dns-cloudflare-credentials ~/nuget/.secrets/cloudflare.ini \
  -d nuget.qsupport.ru --cert-name nuget.qsupport.ru

sudo certbot certificates   # домен должен быть в списке
```

Credentials-файл — **в каталоге проекта**, не в `~/.secrets/`. Содержимое не
выводить. Если каталога `.secrets` на сервере ещё нет — скопируй с любого
проекта, где он уже есть (тот же токен Cloudflare). Продление уже настроено
через `certbot.timer`.

## Шаг 2. Забрать код

Репозиторий — **`github.com/QuantumArt/nuget`**, публичный, клон без токена:

```bash
git clone https://github.com/QuantumArt/nuget.git ~/nuget
cd ~/nuget
git log --oneline   # убедись, что коммиты есть
```

Публичность снимает проблему первого деплоя в пустой репозиторий: клон
работает анонимно, `.credentials.env` для `git clone` не нужен. Он нужен
**только** для `git pull` внутри `deploy.sh` — и то только потому, что глобальный
`credential.helper=store` на VPS перебивает анонимный доступ к приватным
запросам. Если залить токен нечем, закомментируй шаг 1 в `deploy.sh`: код
не меняется часто, а `docker compose up` и заливка пакетов работают без сети
к GitHub. Обход авторизации — DEPLOY-SPEC §3.3, вариант 1.

## Шаг 3. Поднять контейнер и залить пакеты

```bash
cd ~/nuget/site && chmod +x deploy.sh && ./deploy.sh
```

Скрипт поднимет контейнер, скачает пакеты с оригинала (адрес закреплён на
91.216.147.7 через `--resolve`, поэтому скрипт безопасен и до, и после
переключения DNS) и зальёт их в клон. В конце — smoke-тест, который качает
реальный `qa.core 3.6.2` и проверяет, что архив валиден.

## Шаг 4. Подключить хостовый nginx

```bash
sudo cp ~/nuget/site/nginx/nuget.qsupport.ru /etc/nginx/sites-available/
sudo ln -s /etc/nginx/sites-available/nuget.qsupport.ru \
         /etc/nginx/sites-enabled/nuget.qsupport.ru
sudo nginx -t && sudo systemctl reload nginx
```

`nginx -t` обязан пройти **до** reload.

## Шаг 5. Проверка через nginx, ДО переключения DNS

```bash
# минуя DNS, через хостовый nginx
curl -I --resolve nuget.qsupport.ru:443:127.0.0.1 https://nuget.qsupport.ru/

# и содержимое, а не только код
curl -s --resolve nuget.qsupport.ru:443:127.0.0.1 \
  https://nuget.qsupport.ru/v3/package/qa.core/3.6.2/qa.core.3.6.2.nupkg \
  -o /tmp/t.nupkg && unzip -tqq /tmp/t.nupkg && echo "пакет валиден"
```

Проверяй именно скачивание пакета, а не только `/`: главная отдаётся
SPA-оболочкой даже при пустом фиде, и «200 на /» ничего не доказывает.

## Шаг 6. Переключить DNS

A-запись `nuget.qsupport.ru`: `91.216.147.7` → `217.198.6.66`.

**Только теперь** — сертификат уже выпущен, nginx настроен и проверен.
Проверить: `dig +short nuget.qsupport.ru A` вернул `217.198.6.66`.

## Шаг 7. Финальная проверка

```bash
curl -s https://nuget.qsupport.ru/v3/index.json | head -c 200
curl -s 'https://nuget.qsupport.ru/v3/search?q=qa.core&take=1' \
  | python3 -c "import sys,json;print('hits:',json.load(sys.stdin)['totalHits'])"
```

И главное — **проверь сборку**: возьми любой реальный проект, который тянет
пакеты с `nuget.qsupport.ru`, и прогони `dotnet restore`. Это единственная
проверка, которая имеет значение для потребителя фида.

## Откат

```bash
# 1. вернуть A-запись
#    nuget.qsupport.ru: 217.198.6.66 -> 91.216.147.7

# 2. (необязательно) снять прокси
cd ~/nuget/site && docker compose -f docker-compose.production.yml down
sudo rm /etc/nginx/sites-enabled/nuget.qsupport.ru
sudo nginx -t && sudo systemctl reload nginx
```

Откат DNS занимает минуты и сразу возвращает боевой фид. **Данные клона при
этом остаются на месте** — контейнер можно поднять обратно в любой момент.

## Обновление фида позже

```bash
cd ~/nuget/site && ./deploy.sh
```

Идемпотентно: уже скачанные и валидные пакеты пропускаются, уже залитые
версии дают ошибку `AllowPackageOverwrites=false` — это нормально, скрипт
считает их как «уже было».

## Грабли, уже оплаченные

- **`Storage:Path`, а не `FileStorage:Path`.** Официальный гайд BaGet даёт
  `FileStorage__Path`; в этой версии движка переменная молча игнорируется,
  пакеты пишутся в `/app/packages` — слой контейнера. Фид при этом работает,
  ошибки не видно, и всё теряется при первом `docker rm`.
- **SQLite-база должна быть в томе.** По умолчанию `Data Source=baget.db`
  рядом с бинарём — снова в слое.
- **BaGet дописывает `packages` к `Storage:Path`.** Фактический путь:
  `baget-data/packages/packages/<id>/<version>/`. Не ищи по `packages/<id>`.
- **Обрезка zip на таймауте.** `SeleniumExtension 1.0.8–1.0.13` — по 20+ МБ;
  на дефолтных 30s curl стабильно рвётся и оставляет невалидный архив, который
  выглядит как скачанный файл. Остальные пакеты — 26 КБ в среднем. Поэтому в
  `deploy.sh` стоит `--max-time 900` и проверка `unzip -tqq` каждого файла.
- **`xargs -n 1` вместо `-I`:** `xargs -I{} ... {}` с 629 аргументами упирается
  в `command line cannot be assembled, too long`. Скрипт написан на цикле.
- **Пустой поиск отдаёт 0.** `?q=` без запроса не находит ничего — это
  поведение BaGet, а не поломка. Проверять поиском по конкретному имени.
